# LearnOS 项目拷打式深挖问答版

## 1. 架构层深挖

### Q1：你说这个项目是“状态化学习系统”，那你具体有哪些核心状态？

**回答思路：**  
核心状态包括学习会话、文档与切片、知识点、复习项、测验题集与作答、错题重练记录、学习计划、回答评测、模拟面试会话与轮次、事件日志与 agent runs。

**可以这样答：**  
我不是把系统只做成“用户输入 -> 模型返回”的一次性流程，而是把学习过程中的关键对象都持久化了。比如 `study_sessions` 管理学习主题，`review_items` 管理复习状态和优先级，`quiz_attempts` 管理测验结果，`study_plans` 和 `study_plan_items` 管理可执行计划，`answer_evaluations` 管理回答质量评测，`interview_sessions` 和 `interview_turns` 管理模拟面试，`event_logs` 和 `agent_runs` 管理运行观测。这样模块之间才能真正形成回流闭环。

### Q2：为什么不把所有逻辑都写在一个后端文件里，反正也是个人项目？

**回答思路：**  
如果都堆在一个文件里，短期快，长期会失控，尤其是这种多状态系统。

**可以这样答：**  
我一开始就知道这个项目不会停在单点问答，所以我刻意把它拆成 service 层。比如 document 负责资料入库，review 负责复习调度，quiz 负责出题评分，plan 负责计划生成和持久化，evaluation 负责回答评测，interview 负责模拟面试，observability 负责日志。这种拆法的价值不只是代码整洁，更重要的是后面做 V2 时可以低成本扩展，也便于针对单条链路写测试。

### Q3：你说“会话级隔离”，那 SQLite 和 Chroma 两边怎么保持一致？

**回答思路：**  
关键是统一用 `session_id` 作为结构化状态和向量检索的共同约束。

**可以这样答：**  
SQLite 里所有结构化对象都和 `session_id` 关联，Chroma 里每个 chunk 的 metadata 也写入 `session_id`、`document_id`、`source_type` 等信息。这样检索时只查当前会话，删除时也能按会话清理 Chroma 中的向量切片。两边并不是事务级强一致，但在当前单机学习系统里，这种基于 session 的一致性约束已经能很好地保证隔离性和可维护性。

## 2. RAG 深挖

### Q4：为什么不直接把整篇文档喂给模型，而要切块加向量检索？

**回答思路：**  
上下文长度、召回精度、成本和可扩展性都不允许这么做。

**可以这样答：**  
如果直接塞整篇文档，首先上下文长度会很快成为瓶颈，其次会把很多无关内容一起带进去，影响回答聚焦度，还会增加模型调用成本。切块加向量检索的好处是能按问题只取最相关的片段，同时保留来源信息，让问答更可控、更可追溯。

### Q5：网页导入如果抽错了正文怎么办？

**回答思路：**  
这是一个可接受的噪声问题，但我通过“优先正文抽取 + 静态站点优先 + 批量导入限制”来控制风险。

**可以这样答：**  
网页导入第一版我没有追求覆盖所有网站，而是优先支持静态正文页和静态目录页。因为这类页面更容易抽到干净正文，适合技术博客和教程场景。如果正文抽取质量下降，会直接影响后面的摘要、知识点和问答，所以我把这块看作“资料质量入口”。当前策略是先做强约束场景，后续如果继续迭代，再补站点规则和动态站点兼容。

### Q6：你的 RAG 是怎么和学习系统结合的，而不是停留在独立问答？

**回答思路：**  
RAG 只是知识获取入口，后面还要进入测验、复习和计划链路。

**可以这样答：**  
在 LearnOS 里，RAG 的作用不仅是回答问题，还会把回答和学习会话关联起来，并结合当前会话的复习项注入复习提醒。更重要的是，问答历史还会进一步参与学习计划生成和回答质量评测。也就是说，RAG 在这个项目里是学习闭环中的一个环节，而不是最终目标。

## 3. 测验与复习系统深挖

### Q7：错题为什么不单独存一张表，而是先沉淀为 review_items？

**回答思路：**  
因为错题在这个系统里不是孤立对象，而是复习调度的一部分。

**可以这样答：**  
低分题本质上是“高优先级待复习内容”，所以我先把它写入 `review_items`，并用 `source_type=quiz_feedback` 区分来源。这样它天然就能进入复习队列、学习计划和报告链路。后面我又加了 `wrong_question_attempts` 来记录重练过程，这样既保留了“错题是复习资源”的统一性，又保留了错题演进记录。

### Q8：Again / Hard / Good / Easy 这套机制为什么值得做？

**回答思路：**  
它让复习从静态列表变成可调度系统。

**可以这样答：**  
如果没有这套反馈机制，复习项只能按固定优先级排序，无法体现用户真实掌握情况。加入 Again、Hard、Good、Easy 后，我可以根据用户反馈动态调整 review_status、mastery_level、priority_score 和 next_review_at，让复习系统真正具备“越用越懂用户”的能力。

### Q9：为什么说学习计划不是简单的文本生成？

**回答思路：**  
因为我让它具备了可执行性和状态演进能力。

**可以这样答：**  
如果只是让模型生成一段“今天建议学什么”，那它本质上只是一次性建议。我把学习计划拆成头表和 item 表，支持保存、加载、勾选完成、只看未完成项和重排优先级。这样计划不是文本，而是带状态的任务集合，能随着学习进展持续变化。

## 4. V2 深挖

### Q10：回答评测不是让模型“自己评自己”吗？会不会不可靠？

**回答思路：**  
确实存在局限，所以我做的是“规则兜底 + LLM 增强”的方案。

**可以这样答：**  
这是一个典型风险点，所以我没有把回答评测完全交给模型黑盒处理，而是设计了 fallback 规则评分逻辑，再在可用时用 LLM 生成更自然的反馈。这样即使模型调用异常，系统也不会失去评测能力。它不是绝对客观评分器，但对于学习场景来说，已经足够提供方向性的反馈。

### Q11：模拟面试为什么不直接复用聊天接口？

**回答思路：**  
因为面试是有轮次、有状态、有总结的结构化过程。

**可以这样答：**  
普通聊天是连续开放式问答，而模拟面试更像一个有边界的流程：先生成 blueprint，再逐轮作答、逐轮评分、生成追问，最后形成总结。这种链路天然适合独立建模成 `interview_session` 和 `interview_turn`，否则会把所有状态塞进聊天消息流里，很难维护，也不利于后续扩展面试报告。

### Q12：Agent run / step 日志的价值是什么？为什么不只看 event_logs？

**回答思路：**  
event_logs 更偏业务事件，run/step 更偏执行过程。

**可以这样答：**  
如果只有 event_logs，我只能知道“某次问答成功了”或者“某次测验提交了”，但不知道内部到底卡在哪一步。加上 agent_runs 和 agent_run_steps 后，我可以看到一次学习问答是否经过了 retrieve、generate_answer、evaluate_answer，以及每一步耗时和状态。这样无论是性能分析还是定位问题，都更细。

## 5. 工程与测试深挖

### Q13：你为什么同时做服务层测试和接口层测试？

**回答思路：**  
因为两者验证目标不同。

**可以这样答：**  
服务层测试更适合验证业务逻辑本身，比如错题回流、面试状态推进、评测聚合是否正确；接口层测试则更适合验证整个 API 入参出参和链路是否打通，比如 `/interview_sessions`、`/evaluations`、`/agent_runs` 这些接口是否真的可用。两个层次结合起来，能更有效地覆盖核心链路。

### Q14：为什么你还说这个项目没有完全工程化？

**回答思路：**  
因为我很清楚它现在的边界。

**可以这样答：**  
当前它已经有服务层测试、接口层测试和基础运行观测，但还没有做真正的端到端自动化测试，也没有更成熟的部署、告警、权限体系和长期趋势监控。所以我会把它定义成“完成度高的可演示 AI 产品”，而不是“完全生产级系统”。

## 6. 当前版本补充追问

### Q15：既然你做了 `agent_engine`，为什么前台主链路还是 `/chat`？

**回答思路：**  
这不是矛盾，而是“稳定主链路”和“预留演进方向”并存。

**可以这样答：**  
我现在会明确区分这两件事。当前面向用户的稳定学习链路，是 `/chat` 加 service 层编排，因为这条链路已经把资料导入、检索问答、测验、复习、计划、报告、评测和面试都接通了。`agent_engine` 和 `/agent_chat` 代表的是我为后续多 Agent 编排预留的实验入口，但我不会把它包装成当前主链路。这样讲更真实，也能体现我知道什么时候该先保证可用性，什么时候再推进架构演进。

### Q16：RAG V2 听起来很抽象，你怎么证明它不是“换个名字继续混合检索”？

**回答思路：**  
要把“问题类型识别 + 路由策略 + 评测闭环 + 样本沉淀”讲具体。

**可以这样答：**  
我会先说它不是单纯的“向量 + BM25 + rerank”。当前版本会先改写 query，再识别问题类型，比如事实、对比、原因、总结、面试、计划、测验，然后动态选择要不要 Multi-Query、召回多少 top-k、Parent 回填窗口多大、上下文预算多大。跑完评测后，低质量 query 还会沉淀进 `rag_quality_samples`，再在 `RAG质量` 看板里看问题类型分布、低质原因和样本库。所以 RAG V2 的重点是“让检索从静态策略变成可路由、可诊断、可持续调优的系统”。

### Q17：你做 RAG 评测和质量看板，实际怎么反哺调优？

**回答思路：**  
不是只展示指标，而是要形成“评测 -> 定位 -> 调参 -> 再评测”的闭环。

**可以这样答：**  
RAG 评测负责产出 `MRR`、`Recall@1/3/5` 和低质量 case，告诉我“这次改动整体有没有变好”。质量看板负责把低质量 query 按问题类型和低质原因沉淀下来，告诉我“差在哪一类问题、为什么差”。这样我就能判断到底要去改 Query Rewrite、Multi-Query、Parent 回填还是上下文预算，而不是凭感觉乱调参数。

### Q18：回答评测为什么要做“规则兜底 + LLM 增强”？

**回答思路：**  
核心是稳定性和可用性，而不是追求一个完全黑盒的华丽方案。

**可以这样答：**  
如果完全依赖 LLM 评分，一旦模型调用异常，整个评测链路就断了。所以我先做规则兜底，用覆盖度、来源数量、回答长度、结构化表达等信号给出基础分，再在 LLM 可用时生成更自然的反馈文字和 strengths / risks / next_actions。这样系统既有最低可用能力，也保留了更好的表达效果，是一个比较务实的工程取舍。

## 7. 面试中的高压追问

### Q19：如果现在让你把这个项目上线给多人用，你第一步改什么？

**建议回答：**  
我会优先改三件事。第一，把 SQLite 升级成 PostgreSQL，解决并发写和数据可靠性问题。第二，把前端从 Streamlit 迁移到更适合复杂交互的前端框架。第三，补鉴权、任务队列和更完整的日志监控。因为当前项目的核心业务模型已经比较清晰，真正限制多人上线的是存储、前端形态和工程基础设施。

### Q20：如果面试官说“这个项目功能很多，但技术深度不够”，你怎么接？

**建议回答：**  
我会把重点放回状态设计和系统链路上。这个项目表面上功能多，但本质难点不是堆功能，而是把资料入库、问答、测验、错题、复习、计划、报告、评测、面试这些模块用统一状态模型串起来。对我来说，真正的技术深度体现在数据建模、模块边界、链路回流和工程取舍，而不仅仅是调用了多少模型接口。

### Q21：如果面试官说“为什么不用 React 而用 Streamlit，会不会太偏 Demo？”

**建议回答：**  
我会承认这是取舍。当前目标是高效验证 AI 学习闭环，所以我优先选择能快速落地的前端形态，把时间投入在业务模型和系统链路上。这个选择确实更偏原型和演示，但并不影响后端服务、数据模型和业务流程的设计质量。反而因为前端成本更低，我能更快迭代核心能力。

### Q22：如果面试官问“你最自豪的一点是什么”，怎么答更好？

**建议回答：**  
我最自豪的不是单个功能，而是把项目做成了一个真正能持续使用的学习闭环。很多 AI 项目停在“上传文档后提问”，但 LearnOS 已经能围绕学习过程的多个环节持续运转。我觉得这体现了我对复杂业务链路的抽象和落地能力。

## 8. 最后收尾模板

### 收尾答法 1：强调系统完整性
这个项目让我比较有成就感的地方，是我没有把它做成单点 RAG Demo，而是围绕学习场景做成了完整闭环系统。它既能导入资料、检索问答，也能测验、复习、计划、报告、评测和模拟面试。我觉得这更能体现我做复杂 AI 应用的能力。

### 收尾答法 2：强调工程能力
我觉得这个项目最体现我的地方，是我能把一个 AI 想法拆成明确的数据模型和服务边界，再一步步做成真实可运行的系统，而不是停留在一个概念验证层面。

### 收尾答法 3：强调成长性
这个项目还没有完全结束，但它已经形成了非常清晰的演进路线，比如学习计划增强、端到端测试、更强的评测和面试能力。我觉得这也说明我不是只会把项目做出来，还会思考它怎么持续迭代。
